# Case study: reliable rent records when messages fail

**Manual problem.** Rent tracking across spreadsheets, M-Pesa messages and separate agreement files makes partial payments, arrears and follow-ups difficult to reconcile. This is the problem the project addresses; measured customer savings or production adoption are not claimed.

**Implementation decisions.** The workflow separates immutable received payments from invoice allocations and notification delivery. Payments settle the oldest outstanding invoices first, within both payment and invoice limits; excess remains visible as unapplied credit. A durable callback inbox recognizes repeat transaction IDs across matched and unmatched references. A PostgreSQL outbox retries notification failures with a bounded backoff and worker leases. Signing uses one versioned route, a time-limited link, OTP verification, tenant consent and an authenticated owner countersignature, retaining the original and final PDF hashes.

**Exception scenario — tested with synthetic data.** The same payment callback arrives five times concurrently while SMS is unavailable. Only one payment, receipt and automatic delivery job are created. The financial transaction remains committed after the SMS failure; a later worker retries the message without taking the rent again. A reused transaction ID with changed amount/reference is rejected for review. Separate tests show that competing allocations cannot exceed received money or invoice capacity.

**Evidence and limits.** A disposable PostgreSQL 18 database executes all eleven migrations and the application workflow tests, including signing under a non-superuser role with row security enabled. SMS/email are mocked. This demonstrates tested project behavior, not provider approval, live delivery or a certified electronic signature. External transport remains at least-once: a crash after provider acceptance can produce a duplicate notification, although it cannot duplicate the payment.
